## 常见失败模式（打分时重点看）

按经验，这些是把模型区分开的关键点，从最易错排起：

1. **`-2 ^ 2` 算成 `4`** —— 文法规定 unary 比 `^` 松，结果必须是 `-4`。几乎所有"凭直觉写"的实现都会错。
2. **`^` 写成左结合** —— `2^3^2` 得 64 而非 512。
3. **比较运算符做成左结合** —— `1 < 2 < 3` 必须是 ParseError，而不是求值为 `true`。
4. **`not` 的优先级放错** —— 规格要求 `not` 比比较**松**（`not 1 == 2` 是 `not (1==2)`），
   但多数语言里 `not` 比比较紧。这是刻意设置的反直觉点。
5. **短路时跳过了左操作数的类型检查** —— `"s" and true` 必须报错。
6. **`true == 1` 返回 `true`** —— Python 里 `True == 1.0` 为真，必须显式比类型。
7. **`if()` 不惰性** —— 直接求值三个实参，`if(1<2,"yes",1/0)` 会炸。
8. **函数名与变量名共用一个命名空间** —— `evaluate("f(1)", {"f": 2.0})` 必须报
   `undefined function: f`；`evaluate("abs")` 必须报 `undefined variable: abs`。
9. **数字没统一成 float** —— `len("ab")` 返回 `2`（int）而非 `2.0`。
10. **REPL 字符串输出没重新转义** —— 打印出真换行而不是 `"a\nb"`。
11. **REPL 数字格式化** —— 打印 `3.0` 而不是 `3`，或把 `0.5` 打成 `0.5000000001`。
12. **`x = 1` 与 `x == 1` 混淆** —— 赋值判定必须用 `=(?!=)`。
13. **`1.` 被接受成 `1.0`** —— 规格要求 LexError。
14. **`%` 用 C 语言符号规则** —— `-7 % 3` 必须是 `2`（Python 规则），不是 `-1`。
15. **`(-8) ^ 0.5` 返回复数** —— 必须转成 EvalError。
16. **把所有代码写进一个文件再拆不动** —— 规范分扣分项。
17. **用 `eval()` 抄近路** —— 直接判为严重违规：自动判定按实得分，规范分该项 0 分，并在报告中标注。
